## falsification-first phase design

- The phase-1 design is deliberately *falsification-first*: each script targets a claim that is currently inference (ENUM cast, transaction participation) or contradiction (blob appender). Measuring these before benchmarking matters because a wrong capability assumption would silently invalidate benchmark cells — e.g. benchmarking "appender for blobs" that actually errors.
- The blob discrepancy is the interesting one: a spike measuring ERR while the C-API wrapper has `duckdb_append_blob` wired means the failure is likely in the *dispatch* layer (Julia type → append call selection), not the C binding. That distinction changes what codegen must emit.

## blob hypothesis from reading the ccall signature

- **Blob hypothesis found.** `appender.jl:94` calls `duckdb_append_blob`, and `api.jl:7257-7266` declares its ccall signature as `(duckdb_appender, Ref{Cvoid}, idx_t)`. A `Vector{UInt8}` passed where a `Ref{Cvoid}` is expected is a Julia-side conversion question, not a DuckDB one — so the spike's `ERR` may be a *driver binding bug at the ccall boundary*, not a missing capability. That's a materially different finding for codegen (bug to work around vs. feature that doesn't exist).
- The spike's `check_roundtrip` compares with `isequal`, and BLOB reads back as `CodeUnits` — so a value mismatch would have printed `ok? got …`, not `ERR`. The `ERR` was therefore a genuine throw, which rules out "it worked but compared unequal."

## discrepancy resolved, and my own probe was confounded

- **The discrepancy is resolved: both notes were right about different things.** Dispatch *does* reach `appender.jl:94`, so the blob path exists — but `api.jl:7261` declares the data argument as `Ref{Cvoid}`. `Cvoid === Nothing`, so Julia tries `convert(Nothing, payload)` and throws *"cannot convert a value to nothing for assignment"*. Re-declaring the identical C entry point with `Ptr{Cvoid}` round-trips all four bytes perfectly. This is a one-word bug in an autogenerated wrapper, not a missing capability.
- **My probe 4a is confounded.** It failed with `embedded NULs are not allowed in C strings` — that's Julia's `Cstring` conversion rejecting the payload *before* DuckDB ever saw it, so it says nothing about whether the C appender casts VARCHAR→BLOB. I need a NUL-free control to separate "cast unsupported" from "NUL rejected". Same trap is waiting in the ENUM script, which tests that very cast.

> follow-on: the NUL-free control was *also* confounded — it failed on
> `Invalid unicode (byte sequence mismatch)`, i.e. non-UTF-8 bytes rejected as a
> VARCHAR value. Three payloads (ASCII / non-UTF-8 / with-NUL) were needed before
> the VARCHAR→BLOB cast could be observed cleanly. Peel one confound at a time.

## enum cast confirmed; the batch result hid a bigger hazard

- **ENUM cast confirmed** (was `Inferred`): valid labels round-trip; `missing` → NULL works. The C error on a bad label — `Could not convert string 'banana' to UINT8` — also reveals the physical representation: DuckDB stores this ENUM as a `UINT8` dictionary index.
- **Invalid and wrong-case labels vanish silently** — no Julia exception at any step, row simply absent. Enum labels are case-sensitive, so a dbdict dictionary disagreeing with the DB on case would quietly drop rows.
- **The batch result hides a bigger hazard.** `["sad","ok","banana","happy"]` yielded `["sad","ok","happy"]`. A failed `append` never advances the appender's *column counter*, so the next value lands in the slot the failed one vacated. In a single-column table that merely looks like "bad row dropped". In a **multi-column** table it would shift every subsequent value into the wrong column — silent misalignment, not just loss. That needs its own measurement.

## column misalignment confirmed: row counts are not enough

- Input `[(1,"sad"), (2,"banana"), (3,"ok"), (4,"happy")]` produced `[(1,"sad"), (2,"ok"), (4,"happy")]`. Row 2 kept its own `id` but was **paired with row 3's enum value**. The failed `"banana"` append left the column cursor parked on `m`, so `3` was offered to the ENUM column (`Unimplemented type for cast (INTEGER -> ENUM…)`), and `"ok"` filled the slot instead.
- This means a `COUNT(*)` check — the study's gotcha-2 mitigation — is **necessary but not sufficient**. It flags that something went wrong, but a surviving row already carries silently mismatched columns. Correct mitigation is per-step `duckdb_appender_error` polling or validating values before they reach the appender.

## transaction leak (captured at phase close, same measurement run)

Buffered appender rows escape the transaction entirely. There is no discard path —
`api.jl:6820` documents `duckdb_appender_destroy` as flushing on destroy — and
`appender.jl:56` registers a finalizer, so an appender abandoned on an error path
is flushed by the **GC**: measured 0 rows immediately after a rollback, then 5
rows after a forced `GC.gc()`. Non-deterministic, post-rollback data appearance.
Mitigation measured to hold: keep the appender's whole lifetime inside the
transaction body with `try`/`finally` closing it before the transaction unwinds.
