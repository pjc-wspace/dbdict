## 1. THE OPEN ISSUE — writer tier order (decide before phase 5)

**`review-decisions.md` finding 4 records "appender tier = scalar-only tables",
with the appender as the preferred writer. Measurement contradicts it.** That
decision was grounded in the DuckDB docs' claim that the Appender is "much faster
than using prepared statements or individual INSERT INTO statements" — a claim
that was never tested against the registered-scan path.

Measured, at 1 thread (`reference.md` §7.2, all 24 write orderings reproduced
across repeat runs):

| flat profile | appender | `register` + `INSERT…SELECT` |
|---|---|---|
| 1M rows | 195.964 ms · 7,996,936 allocs | **58.115 ms · 14,853 allocs** |
| 100k rows | 19.377 ms | **6.116 ms** |
| 10k rows | 2.051 ms | **1.015 ms** |

3.4× faster at 1M with 538× fewer allocations, and it wins at *every* scale at 1
thread. It is also the **safer** path: an unsupported column type is rejected
loudly at `register_table`, whereas appender failures are silent *and* misalign
subsequent column values (§5.1.2 — a row-count check cannot detect it).

`reference.md` §8.1 proposes this order, for this session to accept, amend or
reject:

1. `register` + `INSERT INTO … SELECT` — all column types in
   `create_logical_type` coverage
2. `register_flat` — plus STRUCT columns whose leaves are all tier-1 types
3. **prepared bind** — the table has a BLOB column, or a LIST column at bulk scale
4. appender — the table needs UUID, and has no BLOB/LIST/STRUCT/MAP
5. literal SQL — everything else

> Deliberately not decided in the driver session: that session's `goal.md` scoped
> codegen work out. The measurement is not in doubt; the decision is this
> session's to make.

## 2. THINGS THIS SESSION'S PLAN CAN NOW DROP OR CHANGE

- **The appender-blob discrepancy queued for the phase-5 harness is settled.** No
  harness work needed. The path is wired (`appender.jl:94`) but throws before
  reaching C, because the autogenerated wrapper declares the `data` argument as
  `Ref{Cvoid}` and `Cvoid === Nothing` (`api.jl:7261`). Prepared bind is the only
  working non-literal BLOB path. Just a never-emit rule. (`reference.md` §5.1.1)
- **Finding 14 is resolved.** `DuckDB_jll` is **1.5.4+0**, engine `version()` =
  v1.5.4 — neither the 1.5.3 in `impl.md` nor the 1.5.2 recorded as "measured".
  The 1.5.2 reading came from DuckDB.jl's `[compat]` *bound*, not the resolution.
  Fix `impl.md`.
- **ENUM stays in the fastest tier — this is better than recorded.** Finding 4's
  notes implied `register` could not carry ENUM. Measured: a Julia `String` column
  registers fine and DuckDB casts VARCHAR→ENUM on insert. ENUM tables do not need
  demoting to the appender or the literal path. (`reference.md` §4.1)
- **LIST via the literal tier always: still correct, and now doubly justified.**
  Beyond the empty-vector and non-ASCII bugs, the appender **segfaults the
  process** at ~1M list appends (§5.1.4). Note prepared bind survived 4,000,000
  list values over the same `create_value` path, so it is available if a
  faster-than-literal list path is ever wanted.

## 3. NEW RULE — the `%.17e` float fix must be RECURSIVE

`reference.md` §5.2.1 documents that a bare decimal literal is parsed as `DECIMAL`
and costs 1 ULP on `DOUBLE`, fixed by emitting `@sprintf("%.17e", v)`. The doc
states this in scalar, per-column terms. **It applies at every nesting depth**,
measured 2026-07-27:

```
typeof({'x': 0.11914626526441173})       = STRUCT(x DECIMAL(18,17))
typeof({'x': 1.19146265264411730e-01})   = STRUCT(x DOUBLE)
```

Inserting the naive struct literal into a `STRUCT(x DOUBLE)` column yields
`ulp_delta = -1`; the exponent form is exact. The same holds for list literals
(`[0.119…]` loses a ULP, `[1.19…e-01]` does not).

**Consequence:** a serializer that special-cases floats at column level but falls
back to `string(x)` for struct fields or list elements corrupts data silently. The
float rule must be applied by the *recursive* serializer, not at the top level.

The reference harness already does this correctly —
`sqllit(::AbstractVector)` and `sqllit(::NamedTuple)`
(`research/duckdb-driver-jl/bench_common.jl:51-53`) both recurse into `sqllit`, so
nested floats reach the `%.17e` method. **Reuse that serializer rather than
writing a fresh one**, and note its other requirement: dispatch must be directed
by the column's `DuckType`, not by the Julia value type, because blob dispatch on
`AbstractVector{UInt8}` collides with a `UTINYINT[]` column.

## 4. HARD CONSTRAINTS THAT NOW BIND GENERATED CODE

Full list with replacements in `reference.md` §8.2 (16 rules). The ones most
likely to change this session's plan:

- Never emit an appender for a LIST column — the process dies at ~1M appends and
  no generated error handling can recover from a segfault.
- Never let an `Appender` outlive its transaction body — buffered rows flush at
  **GC time**, after a rollback, non-deterministically (§5.1.3).
- A row count is **not** sufficient validation of an appender write — a failed cell
  does not advance the column cursor, so surviving rows silently pair the wrong
  values (§5.1.2). Poll `duckdb_appender_error` per step, or pre-validate.
- Generated streaming readers must use `Tables.columns(chunk)` only. A streamed
  chunk declares `Tables.columnaccess` true but `Tables.columnnames` returns
  `(:tbl,)` **with no error** (§5.1.6).
- Generated modules need `using DuckDB` — **not** `using DuckDB, DBInterface`,
  which fails because `DBInterface` is a transitive dependency. Full import list in
  §8.3.
- Alias every column with the dict spelling. DuckDB identifiers are
  case-insensitive even when quoted, and on a case conflict "one will be selected
  randomly" (§5.2.2).
- Run single-threaded. More Julia threads never helped any measured path and hurt
  the registered scan worst — up to 7.8× at small scales (§7.4).
